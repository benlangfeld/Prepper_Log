# PrepTrack reliability and security audit

## Scope and environment

- Audited baseline revision: `c46a7450f5f1c2e39d5b3d9b9d3a6d6dbe5bdbcd`
- Audit date: 2026-11-09
- Environment: Linux sandbox, Node.js 22.23.4, npm 10.9.9
- Scope: local database and migrations, browser sync queue, LAN sync API,
  configuration and secrets, PWA/offline behavior, backups, tests and deployment
  docs.
- This is a static/code-and-test audit, not evidence from physical household
  devices. Two physical phones, including iOS, were not available; the WAN-down,
  LAN-up, iOS mixed-content, camera and IndexedDB-eviction scenarios remain
  unverified.

The changes accompanying this audit are not a certification that the app is
suitable for critical inventory. Findings below distinguish tested behavior
from architecture risks and unverified device behavior.

## Prioritized findings

| ID | Severity | Finding and evidence | Status |
|---|---|---|---|
| SYNC-1 | P1, data integrity | Before this change, `/v1/sync/push` silently skipped malformed changes and returned success (`sync-backend/src/server.js`, push handler). `src/lib/sync.ts` deletes all selected queue rows after any successful HTTP response. A malformed record in a batch could therefore cause the client to discard changes the server never applied. | Fixed: the server validates every change before starting the SQLite transaction and rejects the full batch with HTTP 400. Backend and frontend regression tests cover atomic rejection and queue retention. |
| AUTH-1 | P1, pairing security | Pairing accepted a four-character code and had no attempt throttle (`sync-backend/src/server.js`, `/v1/pair`). The hash is not a defense against online guessing of a weak code. | Fixed in this branch: minimum 16 characters, maximum 128, and a process-local limit of 10 attempts per source IP per 15 minutes. This is not a distributed or persistent rate limiter; use a random code and do not expose the service publicly. |
| NET-1 | P1, transport security | The prior Compose deployment exposed plain HTTP, while the app can be hosted on HTTPS. Browsers block HTTPS-to-HTTP requests as mixed content; bearer tokens would also cross that LAN connection without TLS. CORS previously allowed every origin when no allowlist was configured. | Fixed in this branch: Compose requires TLS files; the server can serve HTTPS; an empty CORS allowlist denies browser origins. Device certificate trust and physical iOS connectivity still require verification. |
| CONC-1 | P1, concurrent inventory | The server resolves conflicts with whole-entity last-write-wins using client timestamps and device ID (`sync-backend/src/server.js`, `shouldApplyChange` and push handler). Two offline phones changing the same product quantity do not merge stock movements; the later accepted value replaces the earlier one. Arbitrarily future-dated client updates can also dominate later edits until their timestamps catch up. The existing LWW test exercises timestamp ordering, not real devices or additive stock operations. | Unresolved design limitation. Use explicit stock-movement events or a conflict workflow and define server-side clock handling before treating concurrent offline edits as lossless. |
| HOUSE-1 | P1, preparedness consistency | Household size and target days live in `localStorage` (`src/store/useAppStore.ts`, `getStoredHousehold`/`setHousehold`) and are absent from the sync entity set (`src/types/index.ts`). Cats, utility outage targets and evacuation-kit targets are not modeled as shared household configuration. | Unresolved product gap. Readiness values can differ between devices and do not satisfy the stated two-adult/two-cat, 30-day, 14-day utility, and 72-hour evacuation targets. |
| DUR-1 | P2, sync durability | Product/location/log writes and queue insertion are separate IndexedDB operations (`src/lib/db.ts`, CRUD functions and `enqueueSyncChange`). A tab/process termination in the gap can leave an on-device edit absent from the sync queue. The local record remains available on that device, but a normal sync will not necessarily upload it until a new full snapshot is queued. | Unresolved crash-window risk; not reproduced under physical device power-loss testing. |
| STORE-1 | P2, credential storage | The sync device bearer token is stored in plaintext in `localStorage` (`src/lib/syncConfig.ts`, `saveSyncConfig`). A script executing in the app origin or access to an unlocked device can retrieve it. | Unresolved. HTTPS protects network transport, not at-rest browser storage or a compromised device. |
| PWA-1 | P2, offline/eviction | The service worker precaches the built app assets and configured fonts (`vite.config.ts`), and product data is in IndexedDB. No `navigator.storage.persist()` request exists in `src/`. No physical iOS cold-start/offline, storage-pressure/eviction, camera, or service-worker-update test was performed. Browser storage can be evicted; users need independent backups. | Unverified on devices. Keep encrypted exports and perform the drill in `docs/SECURE_LAN_SYNC.md`. |
| DEPS-1 | P2, supply chain | Baseline `npm audit` reported 23 root advisories (11 high, 8 moderate, 4 low) and 9 backend advisories (7 high, 2 moderate). Reported affected packages included Fastify, Vite, PostCSS, `fast-uri`, `find-my-way`, `nanoid`, and `source-map-js`; root audit also flagged `sharp` and `vite-plugin-pwa`. | Updated root Fastify, Vite and PostCSS, and backend Fastify and `fast-uri`, using compatible package-manager updates. The current root lockfile still reports 17 development/build-tool advisories (5 high, 8 moderate, 4 low); the backend reports 6 (4 high, 2 moderate). Both `npm audit --omit=dev` and `npm --prefix sync-backend audit --omit=dev` report zero advisories. `npm audit fix` failed with an npm Arborist `edgesOut` TypeError, so no blanket/force upgrade was used. |

No P0 exploit or data-loss incident was independently established in this
environment. “P1” denotes an adoption-blocking design or correctness risk, not
proof that a production incident has occurred.

## Reproduction notes

### Malformed push acknowledgment (fixed)

Before the fix, pair two test devices, then POST a `/v1/sync/push` body with a
valid product upsert followed by a change with an invalid date or mismatched
`payload.syncId`. The backend skipped the invalid record but returned HTTP 200;
the browser then removed every queued row in that request. The regression test
`sync-backend/src/server.test.js` now verifies HTTP 400 and confirms that none of
the valid prefix was persisted. `src/lib/sync.test.ts` verifies the client keeps
queued rows when a push is rejected.

### Pair-code guessing (fixed, with residual limitations)

The baseline accepted any trimmed code of four or more characters and created
unthrottled pair responses. The backend tests now reject short codes and verify
that the eleventh same-IP attempt within the window is rate-limited. Attempts
are tracked in process memory, so a restart or multiple replicas reset/bypass
that limit.

### Concurrent offline changes (not physically reproduced)

With two devices paired to one household, disconnect both from the server,
change the quantity of the same product independently, then reconnect and sync.
The current whole-entity LWW policy selects one payload rather than adding the
two changes. Repeat with device clocks skewed in both directions. The backend
unit test demonstrates timestamp ordering but cannot establish iOS/browser
behavior or preserve both stock movements.

### Device validation matrix still required

- [ ] Two physical phones, including iOS, with WAN disabled and LAN available:
      pair, add/edit/delete products, record usage, and verify both devices.
- [ ] Repeat simultaneous same-product edits with clocks skewed and server
      restart between push and pull; record any lost or duplicated movements.
- [ ] iOS Safari PWA cold start while disconnected; confirm IndexedDB data,
      updates, camera scanning, and behavior under storage pressure.
- [ ] Verify the LAN TLS certificate is trusted on both phones and that
      HTTPS-hosted app requests to the LAN endpoint succeed.
- [ ] Restore both an encrypted app export and a SQLite server backup on spare
      devices/server before relying on backups.

## Validation performed

After the compatible dependency updates, `npm ci` succeeded for both lockfiles.
The root Vitest suite passed (114 tests), backend integration tests passed (10),
the TypeScript/production build succeeded, and Playwright passed all 6 Chromium
tests after installing its browser. The Docker image built and the HTTPS server
returned a successful health response using a temporary local certificate.
`npm run lint` could not run because the repository's script invokes `eslint`,
which is not installed or declared in the lockfile. Docker Compose configuration
validated. Advisory counts are recorded above. Physical device and WAN/LAN
validation were not performed.

## Deployment and recovery

Use the TLS-enabled Docker Compose deployment, exact CORS origin allowlist,
certificate trust steps, and backup/restore procedure in
[`SECURE_LAN_SYNC.md`](SECURE_LAN_SYNC.md). Plain HTTP is not an acceptable
configuration for a browser-hosted household deployment.
